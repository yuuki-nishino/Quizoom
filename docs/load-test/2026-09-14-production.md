# 本番負荷試験レポート（2026-09-14）

100人規模の同時接続で本番環境が問題なく動作するかを実測した記録（Issue #17、task 27）。
設計時のコスト試算（`.kiro/specs/live-quiz-app/research.md` のコスト試算セクション）の裏取りを兼ねる。

## 実施環境

| 項目 | 内容 |
|---|---|
| 対象 | 本番 Cloudflare（Workers 無料プラン）。Worker `quizoom` / D1 `quizoom-db` |
| URL | `https://quizoom.24no-yuuki.workers.dev` |
| 負荷ツール | `scripts/seed-participants.mjs`（実際の `POST /api/join/:joinCode` と WebSocket プロトコルを使用） |
| 実行端末 | ローカル Mac（Node v24.0.0）。単一拠点から100接続を生成 |
| 実施日 | 2026-09-14 〜 2026-09-15 |

模擬参加者は実行端末上のプロセスが生成するため、計測したレイテンシには端末の回線 RTT と処理遅延が含まれる。判定基準に対しては保守的（厳しめ）に出る。

## 試験1: 段階的ランプアップ（joinCode `3M6UWVPYV5`）

基準値: DO Requests 1 / D1 Rows written 69

| 段階 | 参加者 | DO Requests | 基準比 増分 | 累積エラー率 | D1 Rows written |
|---|---|---|---|---|---|
| 1 | 10 | 11 | +10 | 0% | 69 |
| 2 | 30 | 31 | +30 | 0% | 69 |
| 3 | 60 | 61 | +60 | 0% | 69 |
| 4 | 100 | 101 | +100 | 0% | 69 |

**参加者1人あたり DO Requests 1.00 が4段階すべてで完全に一致。** 再接続や取りこぼしは発生していない。

D1 Rows written が動かないのは設計どおり。参加者・回答は D1 ではなく Durable Objects の SQLite ストレージに書かれ（`src/server/session/live-store.ts:145`）、参加時の D1 アクセスは `findEventByJoinCode` / `findThemeSettings` の読み取りのみ。D1 への書き込みは結果確定時の一度きり（`src/server/results/archive.ts:72-91`）。

この試験は100人登録後・出題前にターミナルを誤って閉じ、進行を完走できなかった。ランプアップの計測値は有効なため再取得はしていない。

## 試験2: 進行の完走（joinCode `3WPFPDPNF5`、設問5問）

基準値: DO Requests 306 / D1 Rows written 135 / DO Errors 102

| 時点 | DO Requests | 差分 | DO Errors |
|---|---|---|---|
| 基準値 | 306 | - | 102 |
| 100人登録後 | 406 | +100 | 102 (+0) |
| 1問目終了後 | 509 | +103 | 102 (+0) |
| 5問完走・結果確定後 | 939 | +533 | 102 (+0) |

**進行中のエラーはゼロ。** 100接続・500回答を通して1件も発生していない（要件9.7）。

1問目の +103 は「回答100件 + 進行操作3回（出題・締切・正解発表）」と一致し、ダッシュボード上は受信 WebSocket メッセージが 1:1 でカウントされることを示す（後述）。

### 出題配信レイテンシ

`questionOpened` の配信時刻（サーバーの `serverNow`）から各クライアント受信までの経過時間。500サンプル（100人 × 5問）。

```
p50 =  26ms    p95 = 536ms    最大 = 536ms
最小 =   8ms    平均 = 126.3ms    1秒超え = 0件
```

| 設問 | p50 | 最大 | 最小 |
|---|---|---|---|
| Q1 | 530ms | 536ms | 508ms |
| Q2 | 26ms | 29ms | 21ms |
| Q3 | 10ms | 11ms | 8ms |
| Q4 | 19ms | 20ms | 17ms |
| Q5 | 45ms | 46ms | 45ms |

- **同報のばらつきが極めて小さい。** 1問内で100人全員が最大28ms幅（Q1: 508〜536ms）に収まる。1人目と100人目の配信差はわずか28msで、DO の同報は100接続でもほぼ同時に届いている
- **Q1のみ500ms前後、Q2以降は1桁〜40ms台。** 初回のウォームアップコスト（DO 起動・スナップショット読み込み）と推定。端末の時計ずれであれば全問に等しく乗るはずだが、Q2以降が10ms台まで下がるため Q1 の500msは実コスト

### D1 書き込みの実測

結果確定後、D1 に直接問い合わせて確認した値（対象イベントのみに絞った件数）。

```
result: 1 / result_entry: 100 / result_answer: 500 / 設問: 5
```

`write queries` の実測 669 は、結果確定の 601 クエリ（1 + 100 + 500）にイベント作成ぶんの68を足した値と一致する。**回答500件が1件も欠けずに永続化された**（締切による取りこぼしなし）。

`Rows written` の表示（約1,000）が挿入行数601を上回るのは、D1 がインデックス更新も計上するため。3テーブルとも暗黙のインデックスを持つ（`migrations/0001_init.sql:53-75`）。単純なインデックス本数からの理論値とは一致しないため、実測値としてそのまま扱う。

## 無料枠に対する消費量

受信 WebSocket メッセージには課金計算上 20:1 の圧縮が適用されるため、ダッシュボードの差分をそのまま課金量として扱ってはいけない。接続確立ぶんはそのまま、受信メッセージぶんは20で割って換算する。

```
DO リクエスト（課金換算）
  接続確立         約100（圧縮対象外）
  受信メッセージ   533 ÷ 20 ≒ 27
  合計             約127 / 100,000 日次上限 = 0.13%

D1 書込行数
  約1,000 / 100,000 日次上限 = 約1%
```

**比率で見ると D1 書込が DO リクエストより約8倍タイト**であり、計測した範囲では実質的な制約はこちらにある。

### 1日あたりの開催可能数

| 制約 | 1イベントあたり | 日次上限 | 開催可能数 |
|---|---|---|---|
| DO リクエスト | 約127 | 100,000 | 約780イベント |
| D1 書込行数（5問） | 約1,000 | 100,000 | **約100イベント** |
| D1 書込行数（10問の場合の推計） | 約1,550 | 100,000 | 約64イベント |

設問数が増えると `result_answer` が参加者数×設問数で効いてくるため、D1 側の消費は設問数にほぼ比例する。10問の推計は、実測で得られた「挿入601行 → Rows written 約1,000」の増幅率（インデックス更新ぶん、約1.4倍）を 1,101 挿入行に適用した値。

**ただしこの表は Worker リクエストを含んでいない**（発見事項2を参照）。`run_worker_first: true` によりアセット取得も課金対象の Worker リクエストになるため、実際の上限はこれより低い可能性がある。年数回の開催という本アプリの利用形態では問題にならないが、1日に多数のイベントを開催する運用を想定する場合は Worker リクエストの実測が必要。

## 要件11.3の個別確認

要件11.3（回答画面がモバイル回線相当の条件で3秒以内に操作可能）は同時接続数ではなく初期バンドルサイズと回線速度に依存するため、負荷試験とは別に計測した。

- 条件: Chrome シークレットウィンドウ / Network throttling = Slow 4G / Disable cache
- 対象: `https://quizoom.24no-yuuki.workers.dev/join/3M6UWVPYV5`

| 指標 | 実測 |
|---|---|
| ニックネーム入力が可能になるまでの体感 | 約1秒未満 |
| DOMContentLoaded | 2.93s |
| Load | 2.94s |
| Finish | 4.69s |

保守的に DOMContentLoaded 2.93s を「操作可能」の指標とみなしても3秒以内でクリア。ただし**余裕は0.07秒しかない**。Finish 4.69s は3秒を超えるが、非ブロッキングな後続リソースを含む値のため判定対象外とした。

体感値1秒未満と DOMContentLoaded 2.93s に開きがある。SPA のため入力欄の描画は JS 実行後のはずで、体感値の方が楽観的な可能性がある。バンドルサイズを増やす変更を入れる際は、Performance パネルでの厳密な再計測を推奨する。

## 発見事項

### 1. Errors 102 の正体は「client disconnected」（対応不要の可能性が高い）

試験の合間、何も操作していない状態で DO Requests が 101→306（+205）、Errors が 102 まで増加した。全タブを閉じたところ増加は停止した。

Cloudflare ダッシュボードのエラーカテゴリを確認したところ **`client disconnected`** であった。これはアプリケーション側の例外ではなく、**レスポンス完了前にクライアントが接続を切ったこと**を示す。

試験1では100人の模擬参加者を接続したままターミナルを強制終了しており、100本の WebSocket が正常なクローズフレームを送らずに切断された。**102 ≒ 模擬参加者100 + 進行画面 + 投影画面**と一致する。つまりこのエラーは**試験の終わらせ方に起因する記録**であって、製品側の欠陥を示すものではない。

実際、試験2では進行を完走するまで Errors は 102 のまま増えていない（+0）。スクリプトの SIGINT ハンドラは `ws.close()` で正常にクローズするため、同じ現象は起きない。

なお、クライアントの再接続バックオフには試行回数の上限がなく、上限10秒で永久にリトライし続ける（`src/client/shared/use-live-channel.ts:56, 108`）。理論上は無効なイベントを開いたまま放置したタブが1日あたり約8,640リクエストを消費しうるが、**今回の +205 リクエストがこれに由来すると断定できるだけのデータは取れていない**（放置タブの枚数・時間を記録していないため）。判断するには、無効なイベントのタブを1枚だけ開いて一定時間放置し、リクエストの増加率を測る対照実験が必要。

### 2. Worker リクエストは今回の測定範囲外（capacity 見積もりの穴）

本試験で記録したのは **Durable Objects の Requests** であり、**Worker 自体のリクエスト数は計測していない**。

`wrangler.jsonc` は `"run_worker_first": true` を指定している。Cloudflare の静的アセット課金は「Requests to static assets are free and unlimited」だが、`run_worker_first` に一致するリクエストは Worker が起動するため **Workers pricing に従って課金される**。本アプリはこれを無条件 `true` にしているため（Google OAuth コールバックが SPA フォールバックに横取りされる不具合の回避が理由）、**JS バンドル・CSS・フォント等のアセット取得もすべて課金対象の Worker リクエストになる**。

参加者1人がページを開くたびに複数のアセットリクエストが発生するため、100人規模のイベントでは DO リクエスト（約127）より Worker リクエストの方が大きくなる可能性が高い。日次の開催数を見積もる際はこちらも確認が必要。次回の試験では Worker の Analytics タブでも基準値と差分を記録すること。

### 3. `| tee` 経由だと Ctrl+C でサマリーが出ない（ツール改善）

`scripts/seed-participants.mjs` の終了時サマリーは SIGINT ハンドラでのみ出力されるが、`| tee` へパイプすると出力されない。SIGINT がフォアグラウンドのプロセスグループ全体に送られ、tee が先に終了するため、ハンドラ内の `console.log` が壊れたパイプへの書き込みとなって失敗する。

実害は小さい（各回答行にレイテンシが記録されるためログから復元可能で、本レポートの集計値もログから再計算した）が、SIGHUP/SIGTERM でもサマリーを出す、またはファイルへ書き出す改善余地がある。

### 4. 20:1 圧縮は課金計算のみに適用される

Cloudflare 公式ドキュメントの記述:

> "For compute requests billing-only, a 20:1 ratio is applied to incoming WebSocket messages to factor in smaller messages for real-time communication."

**"billing-only"** が要点で、Analytics に表示される Requests は生のメッセージ数。ダッシュボードが 1:1 で見えるのは仕様どおりであり、`research.md` の前提は正しい。

### 5. 同一イベントに対する負荷試験の再実行はできない

スクリプトは `テスト参加者1`〜`テスト参加者N` の固定名で登録するため、切断後も participant 行が DO に残り、再実行すると全員 `NICKNAME_TAKEN` (409) になる。「参加者データを削除」は D1 の `result` のみを削除し（`src/server/results/archive.ts:138`）、DO 側の participant 行は消えない。再公開も `session_state` の上書きのみ（`src/server/session/live-store.ts:99-106`）。**再試験には新しいイベントの作成が必要。**
